# 詳細設計書

- 分割したとき親だけに置く見出し: なし

## 変更の全体

- 何をどう変えるかを 3〜5 文で書く。子の詳細設計書は、その子の範囲だけを書く

## データ

### インデックス

- 追加・変更・削除するインデックスと、それを使う検索を書く

### パーティション

- パーティションを切るか、切るならその単位を書く

### 移行スクリプト

- スキーマ変更とデータ移行の手順、戻し方を書く。分割したときは、共有するテーブルの移行を親の詳細設計書で先に行う

### ロック

- 移行と更新で取るロックと、止まる処理とその時間を書く

## 実装方式

### ロジックの配置先

- 処理をどのレイヤー・どのファイルに置くかを書く。主張には `file:line` を付ける

### 内部 API

- 自システムの中だけで使う API のパス・入出力を書く

### 例外処理

- どこで例外を捕まえ、どう変換し、どう記録するかを書く

### 排他の実装

- 基本設計書の更新経路の競合を、どの仕組み（楽観ロック、悲観ロックなど）で実現するかを書く

### 権限の実装

- 基本設計書の権限をどこで確かめるかを書く。権限の要る API を、権限の無い利用者の画面から呼んでいないかも書く

## 非機能の実現方式

### 性能

- 基本設計書の性能の保証を、どう実現するか（クエリ、キャッシュ、非同期化など）を書く

### 冗長化

- 基本設計書の可用性を、どう実現するかを書く

### セキュリティ対策

- 基本設計書のセキュリティの方針を、どう実装するかを書く

### 監視への組み込み

- 基本設計書のログ・監視を、既存の監視の仕組みにどう組み込むかを書く

### キャパシティの試算

- データ量とリクエスト数の見込みと、足りるかどうかの試算を書く

## 流用・踏襲する既存コード

- 流用する、または書き方を揃える既存のコードを `file:line` 付きで書く

## PR の切り方と工数

- PR を作る順に並べ、PR ごとに範囲・規模・人月を書く。合計の人月も書く

## シナリオ

- テストのシナリオを `- S-001: 本文` の箇条で書く。子の文書では `S-<子の名前>-001` にする
- 下に 受け入れ基準・種別・層・前提・操作・期待 を書く。同じディレクトリの基本設計書の AC をすべて受ける

## 設計判断

- 覆る可能性のある判断だけを、選んだものと理由を 1〜2 文で書く

## 仮定

- 要確認を立てる条件に当たらず、決め打ちしたことを書く

## 要確認

- 未解決の質問を `- Q-001: 質問` の箇条で書き、下に 推奨・確認先・期限 を書く

## 調査範囲

- 読んだものと、確認していない範囲を 2〜3 行で書く
