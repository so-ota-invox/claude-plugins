# 共通の型

要件定義書（requirements.md）・基本設計書（design.md。以下「設計書」）・実装プラン（plan.md）に共通する書き方。文書ごとの見出しと記入要領は、同じディレクトリの requirements.md・design.md・plan.md に書く。`<plugin>/scripts/specdoc.py` がこの型を機械で照合する。`<plugin>` は sdd plugin のディレクトリ（このファイルの 1 つ上）の絶対パス。

## 置き場

- 要件 1 件につき、リポジトリルート（.git のあるディレクトリ）の直下に `specs/<id>-<slug>/` を作る。`<id>` はチケット番号（英数字とハイフン）、無ければ連番。`<slug>` は英小文字・数字・ハイフン。`<id>` と `<slug>` の境目は機械では分からないので、check が確かめるのは、英数字をハイフンでつないだ形であることと、最後の語が英小文字・数字であることだけ
- ファイル名は requirements.md・design.md・plan.md に固定する
- パスの大文字・小文字は、実際の名前と揃える。大文字・小文字を区別しない macOS でも、Linux と同じく違う名前として扱う。リンク先のパスの文字は NFC で書く
- 設計を子に分けたときは、子ごとに `specs/<id>-<slug>/<子の名前>/` を作り、design.md と plan.md を置く。要件定義書は分けない。階層は親と子の 2 段まで
- 子の名前は、どの語も英小文字で始まる英小文字・数字の 1〜2 語で、2 語はハイフンでつなぐ（`phase2` は使えるが `phase-2` は使えない）。同じ要件の中で重ねない。`mocks` と `specs` は使えない
- 子の名前は親の設計書の「サブ機能分割」で決め、親と一緒に承認する。番号とパスに入るので、承認した後は変えない
- 画面モックは `mocks/<画面>.html` に 1 画面 1 ファイルで置く。外部の CSS・JS・画像を使わない。モックは HTML が正本で、Git で管理する

## 文書の先頭

- 1 行目は `#` の見出しで、雛形の見出し・コロン・件名を書く（例: `# 基本設計書: 請求書の一括発行`）
- 見出しの直後に管理情報を書く。管理情報と最初の `##` の間には何も書かない

## 管理情報

`- 項目: 値` の箇条で、次の順に書く。ほかの項目は書かない。

- 著者: 1 名。回答者は特記が無ければ著者とする。著者以外が回答した箇所には「（回答: 顧客）」のように添える
- 状態: `draft` か `approved`
- 承認者: 状態が `approved` のときだけ書く。`draft` に戻したら消す
- 凡例: 下の文言をそのまま書く
- 親: 子の文書だけに書く。親の同じ種類の文書のリポジトリルートからのパス（子の design.md なら親の design.md）
- 上流: 下の「上流と hash」に挙げる文書を、下の箇条に 1 件ずつ `リポジトリルートからのパス@内容の hash` で書く。要件定義書には書かない
- 元の文書: よそで書かれた文書を取り込んだときだけ書く

凡例の文言:

```text
- 凡例: R = 要件、AC = 受け入れ基準、S = シナリオ、Q = 要確認。子の番号は間に子の名前が入る（例: AC-billing-001）
```

子の設計書の例:

```text
# 基本設計書: 請求書の取消

- 著者: 山田
- 状態: approved
- 承認者: 佐藤
- 凡例: R = 要件、AC = 受け入れ基準、S = シナリオ、Q = 要確認。子の番号は間に子の名前が入る（例: AC-billing-001）
- 親: specs/12-invoice/design.md
- 上流:
  - specs/12-invoice/requirements.md@3f2a9c0d1b7e
  - specs/12-invoice/design.md@8c41d09e2a6f
```

## 上流と hash

- hash は、改行を LF にしたファイルの中身の hash（git の blob hash）の先頭 12 文字。CRLF で取り出した作業ツリーでも同じ値になる。commit hash は squash merge や rebase merge で残らないので使わない
- `python3 <plugin>/scripts/specdoc.py hash <ファイル>` の出力をそのまま書く。人は hash を手で書かない
- 上流に書く文書。これだけを、すべて書く
  - 設計書: 要件定義書。子の設計書は親の設計書も
  - 実装プラン: 同じディレクトリの設計書。子の実装プランは親の実装プランも
- hash が見張るのは、この仕組みの文書のあいだの上流の変化だけ。起草で読んだほかの資料は上流に書かない
- 上流の文書は `approved` でなければならない
- 上流を直すと hash が合わなくなり、下流の check がエラーになる。下流に影響を反映し（起草 skill があれば実行し直す）、hash を書き換え、下流を `draft` に戻す

## 番号

- R = 要件（Requirement）、AC = 受け入れ基準（Acceptance Criteria）、S = シナリオ（Scenario）、Q = 要確認（Question）
- 形は `R-001`・`AC-001`・`S-001`・`Q-001`（3 桁）。子の文書の AC と S は間に子の名前を入れる（`AC-billing-001`・`S-billing-001`）
- 定義する場所
  - R: 要件定義書の「機能概要」と「非機能要件」
  - AC: 設計書の「受け入れ基準」
  - S: 実装プランの「シナリオ」
  - Q: 各文書の「要確認」。Q は文書ごとに 001 から数える
- 定義は、定義する場所の一番上の階層の箇条で `- R-001: 本文` と書く。R・AC・S の番号は、要件 1 件のすべての文書を通して重ねない
- ほかの場所に書いた番号は参照として扱う。コードの中の番号は番号として扱わない
- 参照できるのは、その文書と上流の文書で定義した番号だけ。Q はその文書で定義したものだけを参照できる。下流の文書と別の子の文書の番号は参照しない（要件定義書に AC を、設計書に S を書かない。親の文書に子の番号を書かない）
- 番号はコードとテストに書かない（アーカイブすると参照先が消える）。テストは名前か docstring に前提・操作・期待を文で書く

## 文書をまたぐ対応

- AC は下の箇条 `- 要件: R-001、R-002` で、受ける R を示す。受ける R が無い AC（既存機能に副作用が無いことなど）は `- 要件: なし` と書く
- S は下の箇条に次をすべて書く
  - `- 受け入れ基準: AC-001`（受ける AC）
  - `- 種別: 正常`（正常・異常・境界のどれか）
  - `- 層: 単体`（テストの層）
  - `- 前提: …`・`- 操作: …`・`- 期待: …`（テストの docstring の元）
- 設計を子に分けたとき、親の「サブ機能分割」で子に割り当てた R はその子の AC で受け、割り当てない R（子をまたぐもの）は親の AC で受ける
- AC は同じディレクトリの実装プランの S で受ける
- check がエラーにするもの: 番号の重複、定義の無い番号への参照、下流か別の子の番号への参照、受ける AC の無い R、受ける S の無い AC。受ける側の文書の check で照合する（設計書は要件定義書の R を、実装プランは同じディレクトリの設計書の AC を見る）。受ける側の文書がまだ無いことはエラーにしない
- 意味の対応（AC が R を満たすか、S が AC を確かめるか）は review で見る

## 要確認

- 立てる条件: 範囲や UX を大きく左右する、解釈が複数ある、妥当な既定値が無い、のどれか
- プロジェクトが推測を禁じている項目は、条件に当たらなくても要確認にする
- 優先順位: 範囲 > セキュリティ・プライバシー > UX > 技術。件数の上限は設けない
- 条件に当たらないものは決め打ちして「仮定」に書く
- 未解決のものだけを書く。解決したら消して本文へ反映する
- 解決する工程には、どの工程までに解決するかを書く
  - `requirements`: 要件定義で解決する。要件定義書の承認と、設計へ進むことを止める
  - `design`: 設計で解決する。設計書の承認と、実装プランへ進むことを止める
  - `plan`: 実装プランで解決する。実装プランの承認と、実装へ進むことを止める
  - `release`: 実装の間に解決してよい。リリースを止める
- 文書より前の工程は書けない（設計書には `requirements` を、実装プランには `requirements` と `design` を書けない）。済んだ工程に関わる問いは、上流の文書の要確認にする
- 解決する工程がその文書の工程（要件定義書なら `requirements`）の要確認が残っている文書は `approved` にできない

```text
- Q-001: 取り消せる期限はあるか
  - 推奨: 発行から 30 日
  - 確認先: 経理の担当者
  - 期限: 2026-10-15
  - 解決する工程: design
```

推奨は、推奨する回答があるときだけ書く。

## 仮定

- 要確認を立てる条件に当たらず決め打ちしたことを、短い箇条で書く
- 反証の付いた P0 を人が退けたときは、退けたことと理由も書く

## 状態と承認

- 状態は `draft`（下書き）と `approved`（承認済み）の 2 つ
- `approved` にするのは、人が承認の趣旨をはっきり示したときだけ。AI が自分から変えない
- `approved` にするとき、承認者に `git config user.name` の名前を書く
- 承認で状態を変えたら、その文書を commit する（push はしない）。承認した版が履歴に残る
- `approved` の文書を skill が直したら、`draft` に戻して承認者を消す
- 承認したからマージする。マージは承認の結果で、承認そのものではない

## 見出し

- 見出しは雛形と同じにする（見出しの文字・階層・順序）。足さない、省かない。同じ種類の文書は常に同じ見出しの構造になる
- 書く内容が無い見出しには、本文に「なし」とだけ書く。下に見出しを持たない見出しの本文が空ならエラー
- 設計書と実装プランの雛形の先頭の `- 分割したとき親だけに置く見出し: …` に挙げた見出しは、子の文書には書かない（その下の見出しも書かない）。要件定義書は分けないので、雛形にこの行が無い
- 雛形の見出しの下の箇条は記入要領で、文書には写さない

## 既存コードの調査

- 既存コードについての主張には `file:line` を付ける（例: `app/models/invoice.rb:42`）
- 設計書と実装プランの末尾の「調査範囲」に、読んだものと確認していない範囲を 2〜3 行で書く
- 調査の途中結果は文書にしない

## 指摘

review は指摘を文書の隣の指摘のファイル `<文書名>.review.md`（`specs/12-invoice/design.md` なら `specs/12-invoice/design.review.md`）に 1 件 1 箇条で書き、review のたびに上書きする。途中で agent ごとの指摘を、同じ形で報告のファイル `<文書名>.<agent の名前>.review.md`（`specs/12-invoice/design.fact-checker.review.md` など）に書く。指摘が無ければ「指摘なし」とだけ書く。

```text
- P1 specs/12-invoice/design.md:40: 問題。直し方
  - 根拠: 既存コードの file:line、上流の番号、または型の規則
```

- P0: 重大な欠陥。直すまで進めない。P0 を退けられるのは人だけ
- P1: 品質上の問題。原則として直す。判断が割れたら理由を付けて残し、人が決める
- P2: 改善の提案。直すかは任意
- 検証で誤りと見た P0 は消さず、下に `- 反証: …` を書いて残す。refine はこれを直さず、要確認にする

指摘のファイルと報告のファイルは Git で管理しない。リポジトリの `.gitignore` に次を足す

```gitignore
specs/**/*.review.md
```

## Markdown の書式

HTML へ揺らぎなく変換するため、次の書式だけを使う。外れたら check と html はエラーにする。

- 文字コードは UTF-8 で、BOM を付けない。コードブロックの外ではタブを使わず、段落の行頭に空白を置かない
- 見出しは `#`〜`###`。`#` は 1 行目に 1 つだけ
- 見出し・箇条書き・表・コードブロック・段落の間には空行を入れる
- 箇条書きは `- ` で始める。入れ子は空白 2 つで字下げし、2 段まで。1 項目 1 行
- 表は GFM の表。2 行目は `| --- |` の区切り（ハイフン 3 つ以上）にする。セルの中に `|` を書かない
- コードブロックは 3 つのバッククォートで囲み、言語名を必ず書く。`mermaid` は図として描画する
- 行内の書式はコード（`` ` ``）・太字（`**`）・リンク（`[文字](先)`）だけ
- 使えないもの: 番号付きの箇条書き、`*` や `+` の箇条書き、引用、区切り線、画像、斜体、打ち消し線、生の HTML、バックスラッシュのエスケープ、文字参照（`&amp;` など）、コードの外で単独の `*`、コードの外で語の端に置いた `_`
- リンク先は相対パスか、小文字の http・https・mailto で始まる URL。相対パスは `/` で始めない。リンク先に制御文字とバックスラッシュを入れない。相対パスの区切りは `/` で書き、`%2F`・`%5C` にしない
- 改行は LF にする。Git が取り出すときに CRLF へ変えないよう（Windows の `core.autocrlf` など）、リポジトリの `.gitattributes` に次を足す

```gitattributes
specs/**/*.md text eol=lf
```

## HTML

- 人が読むのは HTML。`python3 <plugin>/scripts/specdoc.py html <ファイル>...` で Markdown の隣に `.html` を書き出す。LLM に変換させない
- Markdown と、リンク先の文書（有無・置き場・件名）が同じなら、バイト単位で同じ HTML が出る
- Markdown を書いたら、人が書いても skill が書いても、最後に必ず変換する
- 書式か置き場に誤りがある文書と、読めない文書は書き出さず、終了コード 1 で終わる。置き場の合っている文書は、前に書き出した `.html` を消し、消したことを出す。`.html` を書けなかったときと、Ctrl-C などで中断したときも、書きかけを残さないように同じく消す
- それ以外の check のエラーがあっても書き出す。相対パスのリンク先が無いときは `パス:行: 警告: …` を出す（終了コードは変えない）
- `specs/` の下の型の文書へのリンクは `.html` へ書き換える。リンク先の `.html` が無ければ（書き出していない、書式の誤りで書き出せないなど）、そのリンクは切れる。番号の定義にアンカーを付け、本文の番号からリンクする
- Mermaid は CDN から読む（バージョン固定と SRI）。読めないときはコードのまま表示する
- 生成した HTML は Git で管理しない。リポジトリの `.gitignore` に次を足す

```gitignore
specs/**/*.html
!specs/**/mocks/**
```

## check

- `python3 <plugin>/scripts/specdoc.py check [--gate requirements|design|plan|release] [--approved] <ファイル>...`
- 照合すること: この文書の「置き場」「文書の先頭」「管理情報」「上流と hash」「番号」「文書をまたぐ対応」「要確認」「見出し」「Markdown の書式」に書いた、文書の形と置き場の規則と、設計書の「サブ機能分割」「テーブル定義」「読み書きするデータ」の形、相対パスのリンク先の実在
- 照合しないこと: 意味の対応、要確認を立てる条件、著者と回答者の書き方、画面モックの中身、コードとテストの中身、承認と上流の書き換えの手順。review で見る
- check は下流の文書を見ない。下流がまだ無いことはエラーにしない
- `--gate` は、渡した文書に、解決する工程がその工程かそれより前の要確認が残っていればエラーにする。どの文書を渡すかは呼ぶ側が決める（その工程の文書と上流）
  - 例: 設計書を承認する前は、要件定義書と設計書を `--gate design` で照合する。実装を始める前は、要件定義書・設計書・実装プランを `--gate plan --approved` で照合する
- `--approved` は、状態が `approved` でなければエラーにする
- エラーは `パス:行: メッセージ` の形で出し、1 件でもあれば終了コード 1 で終わる。エラーが無ければ `ok: 件数` を出す
