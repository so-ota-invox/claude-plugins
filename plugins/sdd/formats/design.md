# 基本設計書

- 分割したとき親だけに置く見出し: サブ機能分割、データ設計、インターフェース設計、主要な用語

## サブ機能分割

- 要件定義書に、まとまり（同じテーブルに書く、同じ業務フロー）が 2 つ以上あれば分割を考える。数値の閾値は持たない
- 分割するときは、子を実装する順に `- 子の名前: 説明` の箇条で並べ、下に `- 要件: R-001、R-002`（子に割り当てる要件。無ければ なし）と `- 依存: なし`（先に作る子。複数なら「、」で区切る）を書く
- 子の名前はディレクトリ名と番号に入る。どの語も英小文字で始まる英小文字・数字の 1〜2 語で、2 語はハイフンでつなぐ
- 子に割り当てない要件（子をまたぐもの）は、この文書の受け入れ基準で受ける。1 つの要件を 2 つ以上の子に割り当てない
- 分割しないときは「分割しない。理由: …」と段落で書く

## 機能設計

### 起点の一覧

- 機能が動き出すきっかけ（画面の操作、API の呼び出し、バッチ、他システムからの通知）をすべて挙げる

### 画面設計

- 画面ごとに項目とふるまいを書く。見た目は写さず、`mocks/<画面>.html` のモックへリンクする

### 業務ロジック・処理フロー

- 処理の流れと業務ルールを書く。状態遷移は `mermaid` のコードブロックで書く

### 入力チェック

- 止める入力と、許す入力の両方を書く

### エラー時のふるまい

- 失敗の種類ごとに、利用者に見せるメッセージと、データがどうなるかを書く

### 権限・可視範囲

- 誰が何を見られ、何をできるかを書く。子は親の権限モデルを参照する

### 読み書きするデータ

- 処理ごとに一番上の箇条を 1 つ書き、下に `- 書く:` と `- 読む:` で `` `テーブル.カラム` `` を「、」で区切って並べる。書く・読むの片方は省いてよい
- 既存で読むだけ・既存で書く・新しく作る・スキーマを変える・削除するテーブルをすべて含める
- カラムはテーブル定義に載せたものだけを書く。子の文書では親のテーブル定義を指す

## データ設計

### ER 図

- この機能が使うテーブルと、関連と多重度を `mermaid` の erDiagram で書く。既存のテーブルも含める

### テーブル定義

- テーブルごとに表を 1 つ書く。見出し行は ``| `テーブル名` | 意味 | 型・長さ | 必須 | 制約 | 差分 |`` にする
- 各行の 1 つ目のセルにカラム名をコードで書く。差分は 既存・追加・変更・削除 のどれか
- 業務上の型の意味（金額の精度と通貨、日時のタイムゾーン、コード値の値域）、業務上の一意キー、削除と保持の方針を、意味か制約に書く
- 変更しない既存のテーブルは、使うカラムだけを差分「既存」で載せる
- 今のスキーマはマイグレーションや ORM の定義を読んで書く

### 書き込む子

- 分割したとき、テーブルごとに書き込む子を書く

### 既存レコードの初期値

- 追加・変更するカラムに、既存のレコードで入れる値を書く

### ダウンタイム

- サービスを止める必要があるか、あるなら許容できる時間を書く

### 更新経路の競合

- 同じデータを更新する経路（画面・API・バッチ）と、競合したときのふるまいを書く

## インターフェース設計

### 公開 API

- 外部の利用者が呼ぶ API のパス・入出力・エラーを書く。自システムの中だけで使う API は詳細設計書に書く

### 他システムとの連携

- 他のシステム・チームとやりとりするデータ、タイミング、失敗したときのふるまいを書く

### 後方互換

- 既存の利用者を壊さないための方針（バージョニングなど）を書く

### 認証・認可

- 誰がどの手段で認証し、何を許可するかを書く

### 権限モデル

- 役割と、役割ごとにできることを書く

## 非機能設計

- 要件定義書の非機能要件をどう保証するかを書く。保証することだけを書く

### 性能

- 要件の目標を、どのデータ量で保証するかを書く

### 可用性

- 障害のとき、どこまで縮退して動かすかを書く

### セキュリティ

- 想定する脅威、対策の方針、受け入れるリスクを書く

### ログ・監視

- 何を検知し、誰に通知するかを書く

## 既存システムとの整合性

### 影響範囲

- 変わる既存機能・データ・外部の利用者を最終確認して書く。主張には `file:line` を付ける

### 既存機能とのふるまいの揃え方

- 同じ種類の既存機能とふるまいを揃えるかを書く。揃えないなら、その理由と、既存側を直すかを書く

### 主要な用語

- 採用する表記と、それを使う場所（DB・API・画面）を書く

## 受け入れ基準

- 受け入れ基準を `- AC-001: 本文` の箇条で書き、下に `- 要件: R-001` で受ける要件を書く。子の文書では `AC-<子の名前>-001` にする
- 確かめられる形（入力・操作・結果）で書く。既存機能に副作用が無いことも書く

## 設計判断

- 覆る可能性のある判断だけを、選んだものと理由を 1〜2 文で書く

## 仮定

- 要確認を立てる条件に当たらず、決め打ちしたことを書く

## 要確認

- 未解決の質問を `- Q-001: 質問` の箇条で書き、下に 推奨・確認先・期限 を書く

## 調査範囲

- 読んだものと、確認していない範囲を 2〜3 行で書く
